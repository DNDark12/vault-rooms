# Vault Rooms secure mesh: design

Status: draft 2 (2026-10-27), after two independent security reviews and their fixes. This fork replaces Vault Rooms' single relay host with an end-to-end encrypted peer mesh. It keeps the plugin's Obsidian integration (live editing in the editor, cursors, room folders, panel and modals) and replaces the server, identity, sync and storage layers.

## 1. Requirements

- Several people, each on their own Windows PC, co-edit notes live on an **offline LAN**. No internet, no cloud account, no CouchDB.
- **No PC is always on.** Whoever is online works together; a PC that comes back catches up by itself.
- **Per-folder permissions.** A room is a folder; each room has its own members and roles.
- **End-to-end encryption.** A PC only ever holds readable content for rooms its user belongs to. Content of other rooms passes through or is stored only as ciphertext.
- **Security is the top priority**: a stranger's device on the LAN can neither read nor change anything; a member can't read rooms they aren't in, can't write where they may only read, and can't plant code (`.obsidian/`, plugins, programs) on other PCs; a lost or stolen PC exposes only that user's rooms.
- **No data loss**: nothing a person wrote is overwritten or deleted without a copy being kept, whatever the network, a crash or another member does.
- Obsidian 1.14.5 desktop on Windows is the reference platform.

## 2. Why a mesh instead of an elected host

Upstream Vault Rooms has one host that holds the only database, merges edits, writes Markdown, assigns versions and enforces permissions on plaintext. With end-to-end encryption the host can do none of that, so its remaining job would be forwarding ciphertext. Electing and replacing such a host adds a leader election, database replication and split-brain handling for little benefit.

Instead every PC is an equal **peer**:
- Peers find each other on the LAN and connect directly over mutually authenticated TLS.
- Each peer keeps an encrypted copy of what the workspace shares (all rooms, as ciphertext), so whoever is online can serve whoever arrives.
- Changes are CRDT updates identified by `(author device, counter)`, so peers can exchange them in any order, more than once, and through any path. Catching up is a version-vector comparison, not a replay of a host's sequence.

What this needs from the network: every PC accepts inbound TCP (TLS) from the local subnet on its port: the first free one of ten (47880 to 47889 unless set otherwise), never another, and UDP for discovery. A pair of PCs that can't reach each other still syncs through any third peer, because peers forward what they receive.

## 3. Identities and trust

- **Device keys.** Each Obsidian install generates an Ed25519 signing key and an X25519 key-agreement key, plus a TLS key and self-signed certificate (whose name says nothing about the device). Private keys live in Obsidian's secret storage, which Obsidian keys by vault and encrypts with the operating system (Windows: per user). They are never in `data.json` or the vault, so a copied vault can't act as the original: it finds no keys and can only be left. On opening, the device id is checked against the signing key.
- **Keys that would weaken the cryptography are refused** wherever a key enters the record: Ed25519 keys of small order (on some implementations their signatures verify for any message) and X25519 keys whose shared secret is known in advance.
- **Workspace.** Created by a founder. Its identity is the hash of its signed genesis record (`workspaceId`). Invites carry the `workspaceId`; every check chains back to it.
- **Workspace record** (`packages/secure/src/workspace.ts`, `chain.ts`) is one linear chain of signed, full-state versions (`v`, `prev` hash, state, signing device, signature). It lists users (name, admin flag, removed), devices (signing, key-agreement and TLS-certificate keys, owner, revoked), open invites, and rooms (encrypted name, members with roles `read`/`write`/`manage`, and key epochs, each a commitment to a room key). Version *n+1* is valid only if a device active in version *n* signed it and its user may make every change it contains (`authorize`):
  - Admins change workspace settings, add and remove users, revoke devices, and create invites for new people.
  - A device is only ever added through an invite marked used in the same version, carrying the joiner's signed record, and the device and user added must match that record exactly. A new device for an existing user needs an invite that user created, so nobody (not even an admin) can register a device under someone else's name and receive their room keys.
  - **An invite names the device that created it, and works only while that device is active and its user still stands**: still an admin for an invite to a new person, and still a manager of each room it grants (rooms they no longer manage are simply not granted). So a removed or demoted admin's open invites, and those made on a stolen computer before it was revoked, die with them. Someone who manages every room an invite grants may withdraw it; removing a person or revoking a computer also withdraws its open invites.
  - Room membership changes only by that room's managers. An admin's invite can grant only rooms the admin manages, and an admin who isn't a manager can't add themselves. Anyone may leave a room.
  - Writers may rotate a room's key: one new key epoch per version, and the last 100 of the 1000 epochs a room can have are kept for its managers, so no writer can use them all up.
  - Users may rename themselves and revoke their own devices. Revocations and removals are permanent. There is always at least one admin, and every room keeps a manager. Revoking a computer (or removing a person) whose join isn't recorded yet records the join first, so it is shut out like any other.
  - A room whose managers have no computer left (all revoked) keeps them on paper only: no one can change its members any more. The app names such rooms before a revocation would make them, and shows them; an admin can only delete them (and share the folder again as a new room).
  - Every version must change something; one user may have at most 30 device records (revoked ones included), 20 open invites, and (unless an admin) create 100 rooms; a version is at most 4 MiB. So no member can fill the record's tables or bloat it for everyone. A join takes effect before it is recorded only within these limits, counting the joins before it (in the order every peer uses).
  - Record time (each version's `at`) never goes backwards, and a peer refuses (for now) a version dated more than 10 minutes ahead of its own clock, so record time stays close to real time. Validity can't depend on when a peer receives a version (peers must agree), so invite expiry for recorded joins is judged against record time.
- **Concurrent changes.** Changes made while peers were cut off from each other produce competing branches. Every peer picks the same winner (`preferBranch`). Each rule looks at one branch on its own, so the rules put any number of competing branches in one order, whatever order they arrive in (a rule weighing two branches against each other, "the one revoking the other's signer wins", goes round in circles when A revokes B, B revokes C and C revokes A, and replaying such branches kept changing who had access):
  1. A branch that takes standing away from anyone wins: it revokes a device, removes a user, demotes an admin, or lowers or ends someone's role in a room (deleting the room included). Only what someone else does counts, so nobody can win by giving up something of their own. A revocation or a removal counts as it is (it is final, even for someone let in within the branch); a demotion or a lowered role counts only if it still holds when the branch ends, so taking something away and giving it back wins nothing.
  2. Otherwise the branch whose first signer ranks higher wins: admins before members, then whoever joined earlier. A signer can't change their rank, unlike a hash, which they could grind by re-signing. A key rotation on its own gets no precedence, so no writer can push aside the changes of someone who ranks higher by rotating a key.
  3. Then the first signer's user id; between two branches started by the same user on two of their devices, the one carrying more versions by other people, so one user can't throw away others' changes; then the device id and the hash.
  **Concurrent revocations add up.** What the losing branch took away (revocations, removals, demotions, lower room roles) is taken away on top of the winner too, by any computer allowed to (an admin, or the room's manager), as long as whoever signed it still has the standing for it: someone the winner revoked, removed or demoted (or whose room it took) doesn't get their way through the losing branch. Revocations and removals count as they are; a demotion or a lower role counts only if it still holds at the end of the losing branch, so taking something away and giving it back changes nothing. And what someone the losing branch took standing from granted at the same moment in the winning branch (making an admin, a higher room role, letting someone in through their invite) is taken back, so nobody can race their own removal to leave a way in behind. The winning branch is replayed to judge this: a grant counts only if whoever made it still had the standing for it there, so what someone they made a manager or an admin granted in turn is taken back too, and a role raised and then lowered again comes back to where it was; someone let in counts as granted by whoever made the invite, not by whoever's computer recorded their joining. Each change is checked like any version, on top of those made before it, so one change that can't be made (for someone the winner removed, say) doesn't stop the others. Every computer allowed to makes them at once (the same change made by several settles like any race), so someone being revoked gets no time to take the revoker's standing first. The workspace always keeps an active admin and every room a manager.
  Conflicts reaching more than 64 versions back are refused. A device makes no change of its own to the record (recording joins, withdrawing expired invites, new room keys) until a device the record lists has answered its hello since it started, or since it was last asleep (every peer is then asked again); a device joining through it doesn't count, since it only has what it was given. It doesn't wait when the record lists no other active device, or listed none when it started and it hasn't been asleep since. Made on an old record, such a change would only start a branch. Besides, a device whose versions lost makes each change again on top of the winner (`rebaseChange`), field by field; a version that started a new room key (a removal does) starts one again, with a fresh key, in the same change, and standing the winner took away (a room role, being an admin) is never given back. Joins recorded in versions that lost wait again until an admin or the invite's creator records them again, unless the lost branch itself took the person back out (revoked or removed them or, for a new user, took a room they had from them or lowered it, by someone else's hand; deleting a room doesn't count): then the invite that let them in is withdrawn, so its link can't bring them back. Withdrawing is best effort: until a computer of an admin or of the invite's creator does it, the link works again; see SECURITY.md. The user is told only if a change can't be made again.
- **Room keys** (`keys.ts`). A random 256-bit key per key epoch, delivered to each entitled device as a key wrap (X25519 ECIES with HKDF-SHA256 and AES-256-GCM), signed by the wrapping device. A wrap names the commitment of the key it carries and counts only while the record's epoch has that commitment, so after two rotations raced, every wrap and receipt of the key that lost stops counting everywhere. Such wraps are set aside and kept (on disk too), not deleted: they count again if the record names their key again, as when a room whose creation lost a race is made again with the same key. Wraps of a room's newest key to or from someone who lost access are kept too, until that key is replaced, as they show who holds it, and so are those of a room deleted recently enough for a fork to undo that; other wraps that can never count again are let go. Recipients check the unwrapped key against the commitment, so a wrong key is useless. A device that makes a key stores its receipt (below) before the change naming the key is made, so a crash can't lose the only copy of a key the others may already have the commitment of; on disk, such a receipt waits aside until the record names its key. A device that holds a key files a wrap of it to itself, a *receipt*; a key counts as delivered only once its recipient's receipt exists, because a wrap from someone else proves nothing (it could carry a wrong key). The lowest-id online holder wraps for devices without a receipt at once, and every other holder steps in after a minute, so no single member can keep a key from anyone. Each device keeps at most one wrap per (room, epoch, recipient, wrapper); a wrap that doesn't verify (yet) is kept aside by its contents, so it can never take the place of a genuine one, and apart for each device that sent it (at most 500 each, the oldest going first), so no one can push out wraps others sent. A device's own keys are checked against the record whenever it changes: a key the record no longer backs (its rotation lost a race) is dropped, and what was sealed under it is sealed again under the right key. Removing a member or revoking a device starts a new key epoch; **new content is sealed only under the room's newest key**: a device that doesn't have it yet keeps its edits until it arrives.

## 4. What is encrypted

Everything inside a room: note text (Yjs updates and snapshots), attachments and other files (encrypted blobs), file names and folder structure (the room index), the room's name, and cursor positions. AES-256-GCM with a random 96-bit nonce; the associated data binds each ciphertext to its room, document, author, counter and key epoch, so it can't be replayed elsewhere.

Peers can see: which devices are online, which rooms exist (as random ids), how many documents a room has, update sizes and timing, and who authored each update.

## 5. Room content model

- **Index document** (one Yjs doc per room, encrypted like any other): `fileId -> {path, kind, deleted, blob, base}`. Renames, creates and deletes are edits to the index, so concurrent changes merge instead of fighting.
- **Notes** (`.md`): one Yjs document per file, bound to the editor with y-codemirror (reused from upstream).
- **Other files**: whole-file versions stored as encrypted blobs, kept per author (a blob is named by its author and a keyed hash of its plaintext, `HMAC-SHA256(room key, bytes)`), so no one can take the place of another member's blob by sending something first, and receivers can verify it. Each version records the one it replaced (`base`); when a version replaces one other than the version a computer made itself, both were made at once, and that computer keeps its own as a conflict copy.
- **Updates** are signed by the author device and numbered per document per author. Peers verify the signature and that the author's user currently has `write` in the room; read-only members' updates are dropped, and so is everything from someone revoked, removed or made a reader, even what they made while they could write. So that a computer catching up later still gets that earlier work, a writer holding it passes it on as its own: a snapshot of each document holding some of it, and a copy of each file version of theirs still in use. The writer with the lowest device id among those online does it; the others step in if the work is still there ten minutes later. It goes one document and one file at a time, with a turn for the app in between, so a member who leaves a lot of work doesn't hold a computer up; a document or file version that can't be passed on (too large, no room left for it) isn't tried again until Obsidian starts again. A snapshot by someone who may no longer write never takes the place of another, and a snapshot dropped as contained in another is remembered, so it isn't taken in and passed around again. **A device stores what it makes before it sends it**, so a crash can't lose an update a peer already has, and a counter is never handed out twice; a write that fails is tried again, and the update waits until it succeeds. What it receives it passes on at once (its author has it stored); a write of it that fails is tried again too, except for an attachment's, which isn't held in memory meanwhile: the attachment is fetched again after a restart.
- **Snapshots** compact a document: a writer encrypts the full state and lists the update counters it covers. That list is only the author's claim. A member decrypts each update a snapshot claims to cover and drops it only if the snapshot really contains it (`Y.snapshotContainsUpdate`); what isn't in it stays. So a lying snapshot can't take anything away from a member, and no counter can be pushed up from outside. A device that only relays a room (and can't decrypt it) takes the claim, but only for the snapshot's own author and only for updates it holds; a lying snapshot can cost the relayed copy of its author's own content, never anyone else's or a member's own history, and the claims are forgotten if the device joins the room.

## 6. Connections and sync between two peers

(`transport.ts`, `discovery.ts`, `peers.ts`, `mesh.ts`)

1. **TLS 1.3.** Each device has its own self-signed ECDSA P-256 certificate; the workspace record lists each device's certificate fingerprint. There is no certificate authority, so instead of Node's chain check the dialling peer checks the exact certificate against the fingerprint of the device it meant to reach, before it sends anything.
2. **Authentication bound to the connection.** The dialler signs the TLS session's exported keying material together with both device ids; the acceptor answers with its own signature over the same. A signature only verifies on that very connection, so nobody in the middle can relay someone else's authentication. Every device sends its public key (its id is the key's hash). A device that isn't a member on this side may then only show that it is: a joining device presents its join record; a member this device doesn't know of yet (it joined while this device was away) sends the record's versions, each checked as always, and taken only if they extend this device's record (a branch that would replace part of it comes from members alone); anything else ends the connection. Its hello is answered (so it learns what this device lacks) only if the hello shows it holds this device's record: one of its latest 64 versions after the first is one of ours. Anyone else hears nothing, and a device the record lists but no longer counts (revoked, or its user removed) is turned away at once.
3. **Limits.** Length-prefixed JSON frames, read with one copy per byte. Until the other side is a member, frames are at most 64 KiB, or 16 MiB once its hello has shown it holds this device's record (a message of record versions). Until then the connection counts against at most 16 such connections, and it must become a member within 10 seconds; anyone can generate a key, so authenticating alone earns nothing more. Members get 64 MiB frames and heartbeats; a peer silent for 45 seconds is dropped. Requests that make a peer send a lot (record history, room contents, room comparisons) are rationed per connection.
4. **Sync.** Both sides exchange workspace record heads (each sends what the other lacks, checked by hash before anything costly; conflicting branches are settled as in §3, and only new versions are passed on), pending joins (one per invite, the one every peer picks) and key wraps, then per-room digests, and for rooms that differ, per-document version vectors, snapshot keys and blob names. Each side then sends exactly what the other is missing.
5. **Live.** Updates and cursor positions are pushed as they happen and passed on to the other connected peers that don't have them yet. Cursor messages count only if fresh (within a minute) and are rationed per author.

**Discovery.** Every 15 seconds each peer announces "device D listens on port P" by UDP multicast and broadcast, signed by its device key and tagged with a hash of the workspace id. Receivers drop anything not signed by a current member or older than two minutes, and limit what each sender address may send. A valid announcement only leads to a dial, which must still pass steps 1–2. Because anyone can replay a member's announcement from another address, an address never replaces one that worked: each is tried, and backs off, on its own. Peers can also be given by address where multicast is blocked, or where the discovery port can't be used (discovery then just stays off). One connection is kept per peer: if both dial at once, the one dialled by the lower device id stays.

**Address book.** Peers tell each other where the devices of the workspace can be reached: each its own addresses, and per device the address that worked last and the latest one announced or told of. They tell it when they connect, and again whenever it changes. A told address, like an announced one, only leads to a dial pinned to that device's certificate, and only for current members. So devices go on reaching each other when the one that brought them together is away. They also find each other again after a restart where discovery doesn't reach: each device keeps the addresses in its settings, with those of the invite link it joined with.

## 7. Joining

(`invite.ts`) An admin creates an invite: a random 32-byte secret from which both sides derive an Ed25519 "invite key". Its public half, the expiry (at most 30 days), the creating device, and the rooms and roles it grants go into the workspace record. The link (`obsidian://vault-rooms?mode=join-secure&ws=…&i=…&s=…&p=…`) carries the workspace id, the secret and a few current peer addresses; it must reach the new person privately.

The new device makes a join record (its user name, its public keys) signed with both the invite key and its own device key, so the secret never travels and nobody who sees the record can reuse the invite. It checks that the record it receives is the workspace the link names and that it knows this invite. Peers treat a valid, unexpired join of an unused invite (whose creator still stands, §3) as membership straight away: the signed record plus such joins is what they act on. If several joins use one invite, every peer keeps only the one with the lowest hash. Joins a stranger presents for invites nobody knows aren't kept. Room members' devices then wrap the room keys for the new device, and an admin or the invite's creator records the join in the chain. A version that marks an invite used must carry the joiner's record, and the device and user it adds must match it exactly. No admin needs to be online at the moment of joining. A user adds another device of their own the same way, with an invite they create for themselves.

## 8. Local storage

Per workspace under the plugin folder: the record (`chain.json`), joins and key wraps (each swapped in whole, through a temporary copy), the encrypted update logs and snapshots (one log per document, appended; rewritten with a line of compaction marks when envelopes are dropped), encrypted blobs (one file each, read only when needed), and what each room folder last synced. File names spell ids so that two ids differing only in case never share a file on Windows. Every append starts on a new line, so one torn by a crash can't take the next with it, and a rewrite interrupted half-way is recovered from its old copy. A document whose log can't be read when the workspace opens (held by another program, say) is left out of syncing until it can be: its note isn't written, a change to it here isn't shared, and its log isn't rewritten meanwhile. It is read again every few seconds, and taken in as soon as it can be. Per room there are limits: 256 MB of document history and, for rooms this device is in, 4 GB of attachments (past them new changes are refused, and the user told); for rooms it only relays, 1 GB of attachments, oldest dropped first. Attachment versions no file of the room uses any more are dropped after a week.

## 9. In the vault (`apps/obsidian-plugin`)

- **Room folders.** A room shared with you gets one folder under the folder for shared rooms, named after the room with anything that could mean another place removed (a room named `..` becomes `Rooms/Room`); if no usable folder can be found, the user is told instead. No room folder may be inside, around or the same as another's: sharing, mounting and moving are all checked, and a move that would put one room inside another is undone. Nothing from `.obsidian/` or any dot-folder is ever synced; every incoming path is checked (no `..`, no dot-segments, drive letters, reserved or short names, invisible characters) before anything touches the disk.
- **File types.** Only types that can't run anything are shared or written: notes, canvases, bases, text and data, PDF, EPUB, Office Open XML documents, images, audio, video and ZIP. Programs, scripts, shortcuts, web pages and documents that can carry macros are neither shared from a computer nor written to it.
- **Deletions.** A file is removed only when the room's index says it was deleted, never because something is missing (a key that hasn't arrived, a half-loaded index, a lost store), and only into the trash. A file changed or worked on here (within ten minutes) when someone else deletes it is shared again instead. A file someone else deleted stays tracked until it is actually trashed here: one that can't be read or trashed now (in use) is tried again, and never shared again as a new file. Deleting a room's folder on one computer hides the room there and deletes nothing for anyone; it can be shown again from the panel.
- **Names and renames.** Two files whose names differ only in case (or form) are told apart by a name with the start of one's id, cut to fit the limits of a name and a whole path, and no other file's; every computer picks the same. A note renamed into another type of file, or another file into a note, gets its old name back (they are shared differently: make a copy instead); a file an earlier version renamed so is still read as what it is shared as. A rename blocked by another file in the way (in use) waits: neither file is taken for the other or written over, and a change made meanwhile follows the file to its new name.
- **Failures.** Writing, reading or trashing a file that fails (in use by another program, a full disk) is tried again by itself, after a second and then less often, up to every five minutes. The panel shows each room's files that keep failing, those whose version here isn't shared, and a folder that doesn't sync at all (what it last synced couldn't be read), with Try again and Details, until they are dealt with.
- **Changes that can't be shared** (a note over 6 MB, the room's storage full) stay on that computer, are never overwritten, and the user is told. Only what was actually shared is remembered as synced, and something this computer made for a file (the file's index entry, a note's edits, an attachment's version) counts only once it is stored, and so do the edits of a note it received (and, for an attachment, an update of the room's index, which names its version). A note isn't remembered as synced at all while an editor's edits of it wait for the room's newest key, as they are held in memory only. A file remembered before that, in a session that ended, is taken as unchanged only once the shared copy matches it (otherwise it is kept as a copy), is never trashed because someone else deleted it (unless all it lacked were edits it received, which were theirs), and is shared again as a new file if its new entry never got stored. Only what was made or received for that very file counts (a note's edits, the index update and attachment version made for it), so one slow write of a note doesn't put every other file in doubt; for attachments received, a slow write of an index update does put those remembered meanwhile in doubt, until it is stored. A room folder waits (briefly) for what is being stored to be stored before it saves its state at shutdown, and a plugin that was just updated (or turned off and on) starts only once its previous instance has finished storing. Nothing is written from a note that is only partly readable or whose own edits are still waiting for a key. A room folder loads what it last synced before it does anything else; if that can't be read, the folder doesn't sync at all (and says so) rather than guess. Once a room's replica is let go (access ended, or the room is being made again), its folder does nothing more but save its state, and a folder shown again for the room waits for that.
- **Changes made outside the editor** (another program, a plugin writing the file) while the shared version has moved on and isn't written to the file yet are settled like a change made on both sides: the shared version is written and the local one kept as a copy, so such a write can't undo someone else's edit. A save made outside the editor changes the note line by line, each changed line replaced whole and tied to the line it replaced. Two or more such saves made at the same moment on different computers that change the same line (a plugin writing two different dates, say) aren't mixed: one of the lines is kept, the same on every computer (the one with the lowest Yjs client id, which every computer can tell from the lines themselves); each other computer keeps the note as it had it, with its line and without the others', as a copy, also when the note is open in an editor, and then takes its own line out again (and any line it put in its place since). The line is taken out only once its copy is written: if the copy can't be written (a full disk, say) or Obsidian stops before it is, both lines stay, and the clash is settled once the copy can be written (it is tried again with every pass of the folder, whenever something in the room changes, and when Obsidian starts again, unless what brought the other line has been folded into a snapshot by then: both lines then stay). A copy is only ever written under a name the room shares. If the room's folder is away at that moment (hidden, or being moved), the clash waits, both lines showing, until the folder is back (and is left as it is if the winning line is gone by then; a clash seen in a snapshot or with typed text that waits through a restart of Obsidian stays as two lines). Nothing else in the note is taken out. Lines only one of them changed stay changed. A line one computer's plugin moved elsewhere unchanged (a card moved to another column, say) while another changed it where it was, or moved it too, is kept once: the line changed where it was stays (of two moves, the lowest client's), and the move is kept as a copy. Only the computer that moved a line can tell it moved, so the move gives way. A line moved and changed in the same save counts as a new line: both stay. Lines added at the end of a note at the same moment are all kept; but when the note ended with a line break and each adds a last line without one, Yjs puts the two side by side on one line, and they stay so until someone splits them (no computer can tell that apart from text typed there). A whole line that reaches a computer inside a snapshot, or in content passed on, counts the same way if it wasn't there before it came, unless the snapshot also holds that computer's own save: it can't tell then whether the other line replaced the old one or was only put above it, and both lines stay until someone removes one. Text typed in an editor inside a line that a save on another computer replaced at the same moment gives way the same way: the saved line is kept, and the typed version is kept as a copy. A line typed above it is a line of its own and stays; what was typed at the start of the line (an indent, "# ") stays in front of the saved line where Yjs puts it there, and otherwise gives way too, with a copy (it would land at the start of the line after); a new line started at its end (Enter, then typing) goes with it into the copy. Text typed at the very end of a note at the same moment as another computer's save adds a last line there without a line break runs together with that line the same way. Text typed anywhere else in the note stays. Each computer remembers its saves of the last 30 days across restarts (saves that change more than a few hundred lines aren't remembered), so a clash is noticed when the computers meet again even if Obsidian was restarted in between. Until the computer whose line gives way sees the other's (it may be off, or not see it until it is back), the others show both lines, one after the other, never run together (but for the last line of a note without a final line break, shown on one line until then). Writes of other files are checked as they happen too: a file saved again while its copy was being kept is left for the next pass, never overwritten.
- **Read-only rooms.** Notes open read-only (typed changes are rejected before they reach the shared text); a reader's change to a file is put back, with their version kept as a copy on their computer only.
- **Editors.** An editor is bound to the shared text (which replaces what it shows) only when nothing can be lost by it: it shows the shared text already, or its file's text and that text came from the shared note (last synced, or being written by the room folder). An editor still loading a note (empty for a moment), with typing not yet saved, or showing a change made while not co-edited waits; the room folder shares that change, or keeps it as a copy, first. Nothing an editor holds is taken into the shared text when binding. Only fully readable notes are bound, and only after the folder's first pass; an editor already bound stays bound while new content waits for a key. Notes are shared with `\n` line endings, as the editor holds them, whatever the file has. Changes that would cut a surrogate pair (half an emoji) are widened to whole characters.

## 10. Limits and known residual risks

- A removed member keeps whatever they had already synced; new keys only protect what comes after.
- A room can have 1000 key epochs. A new one starts only when someone loses access to the room, so it takes a very long time to reach; after that, taking someone out of the room needs a new room.
- Plugins that run code found in notes (Dataview JavaScript queries, Templater user scripts, and the like) would run code any writer of a room puts in a note. Turn such features off for room folders, or don't use those plugins in vaults that share rooms.
- A malicious peer can withhold things or delay a newer record for peers that only talk to it; it can't forge or read them. A malicious writer can make computers that only relay a room drop their relayed copy of that room's history (members' own copies are never affected), and can spend the room's storage limits.
- A writer who signs two different updates under one counter only splits peers on that writer's own content.
- A joining device trusts the first member it reaches until it meets others: a computer revoked after the invite was created could feed it an outdated record for that long (seconds on a working network).
- A device that missed more than 64 changes of the workspace record while it was away, or made a change of its own meanwhile, catches up only from a device it already knew (from one of an earlier version, also when its missed changes don't fit 16 MiB per 500 versions). Members that joined meanwhile can reach it once it has.
- Record versions go out in messages of up to 500 versions, as before: a branch is judged by what one message holds. Only a message too large for the frames the other side reads (64 MiB, or 16 MiB while its record doesn't list this device yet) is cut by size, where before it couldn't be sent at all. A device whose record moves while such a cut message arrives can judge its first part alone; it settles at its next connection. So in a workspace whose versions average more than about 128 KB (hundreds of rooms with long key histories), a device far behind catches up in parts.
- A copy of a vault, or a vault folder moved outside Obsidian and opened as a new vault, has to join the workspace again: the device's keys are tied to the vault in Obsidian's secret storage.
- The listening port accepts connections on every network interface; the firewall rule should be limited to the local subnet (see the README).
- Desktop only.
